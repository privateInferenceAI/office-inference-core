# Phases B and C: lookup, streaming progress, and the budget bug underneath

Phase B added a third tool (`lookup_value`), a two-figure fix, an ambiguity guard, an automatic lookup before a
refusal, and the honesty rule for questions that name an event the evidence never states. Phase C added opt-in
tool streaming with progress frames, the operator documentation, and the automated acceptance run. Both were
measured on the same 52-run suite, three runs per configuration, and both were tested before the next phase
started. This is what happened.

## What the numbers say

| Configuration (Claude Haiku unless noted) | Passes (3 runs) | Average |
|---|---|---|
| Single-shot, before the day's changes (Nova Lite) | 32, 25, 31, 29 | 29.2 |
| Single-shot, contract + multi-passage rule | 36, 36, 34 | 35.3 |
| Tool loop, search and read only (Phase A) | 44, 44, 42 | 43.3 |
| Tool loop, with lookup and honesty rule (Phase B v1) | 41, 40, 42 | 41.0 |
| Tool loop, lookup on, four steps | 39, 40, 41 | 40.0 |
| Tool loop, lookup off, four steps | 40, 37, 35 | 37.3 |
| **Tool loop, final configuration: six steps, lookup off** | **41, 40, 39** | **40.0** |

Two things are solid. The loop is worth about five points on the final configuration and about eight at its best
observed; single-shot cannot exceed 36 on this suite. And the differences *between* loop configurations are inside
run-to-run variance, which is wide: identical runs of one configuration have scored 37 to 44. The honest summary is
"the loop works, the exact configuration is a coin-toss between 40 and 43", not "43.3 is the number".

The test corpus changed twice after Phase A (the redaction canary was restored to make the stream probe
meaningful), so the Phase A row is a reference point, not a controlled comparison.

## Why lookup did not pay off

`lookup_value` was built for the one remaining probe: a pinpoint row inside a 41,000-row coordinate table. It
finds the exact figures literally, comma-insensitive, and a two-figure row is looked up as the intersection of two
matches. The probe still fails, because the row is inside a bounded group and the model reads the wrong line from
that group. On ordinary questions it also cost points: this corpus has the same census figures in many documents,
so quoting 59,473 identifies twenty tables. The ambiguity guard stops the tool anchoring on the wrong one, but the
model then has less to work with than a plain search would have given it.

So lookup stays implemented, tested, documented and switchable (`OI_TOOL_LOOKUP`), default **off**. It is the
right instrument for unique identifiers and it is the wrong instrument for this corpus's duplicated census tables.
The real fix for the large-table probe is row-indexed storage or a table-aware read tool, which is recorded below.

## Streaming

`/ask/stream` keeps its existing frames unless the client opts in with `"tools": true`. With the opt-in the stream
carries `start`, a `progress` frame per model turn and tool call, a `sources` frame with the evidence the tools
returned, then the redacted answer and `done`. Token streaming is traded for progress streaming on this path,
because the loop needs complete messages to parse tool calls from. The streaming probe passes 4 of 4 rights:
END-TO-END, TTFT, INCREMENTAL, and REDACTED (after the canary document was restored to the corpus).

## The budget incident underneath all of it

The Phase B acceptance run came back with 21 of 52 questions degraded and a reason of `budget`. Two defects were
under it, both real.

1. The development analyst ceiling of 10 USD was spent (9.6) by one day of measurement, because the tool loop
   multiplies model calls. Raised to 100 USD on the owner's instruction (PR #175), applied live.
2. The gateway identity was given the team's *remaining* budget while the gateway records spend against the
   identity, so the same spend was subtracted twice and the budget fired at half its nominal value. Every role
   also shared one identity name, so analyst spend was compared against reader's remainder. Fixed in PR #173:
   one identity per role, given the ceiling.

That second defect is the kind this project exists to catch: the acceptance run looked like a provider outage, and
the numbers in the error were the thing that proved it was ours.

## Live configuration and rollback

- Analyst: Claude Haiku 4.5 (`bedrock/us.anthropic.claude-haiku-4-5-20251001-v1:0`), inference profile.
- `OI_TOOL_LOOP=on`, `OI_TOOL_MAX_STEPS=6`, `OI_TOOL_MAX_CALLS=10`, `OI_TOOL_LOOKUP=off`.
- Development analyst ceiling: 100 USD, 30-day period.
- Rollback: `OI_TOOL_LOOP=off` and recreate the API (single-shot, same model); or revert the analyst manifest entry
  to Nova Lite and re-render; or set the gateway policy version back for Claude access.

## Known limits and next work

- A pinpoint row inside a very large table: needs a row index in the chunk store or a table-aware read tool.
- The loop costs about 1.6 times the suite time (178 to 188 seconds against 110 single-shot) and roughly 2 to 3
  times the model calls per answer. Six steps and ten calls bound it.
- Token streaming with tools is not implemented; the opt-in stream trades tokens for progress frames.
- Lookup's default is off; turning it on is a deployment decision with a measured cost on this corpus.
- The next measurement methodology should be a majority over three runs, because single runs vary by seven points.
