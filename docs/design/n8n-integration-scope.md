# Step 2 scope: n8n as the client-owned automation layer

**Status:** scope for review. Implements decision 0011. No runtime change has been made yet.
**Estimate:** about two and a half working days for the baseline (the per-workflow registry and provisioning validation add half a day), plus one day if the optional chain bridge is included.

## Goal

Add a client-owned n8n instance to the product deployment, wire it to our gateway and API, ship the first
workflow templates, and prove one governed end-to-end flow with evidence. The client gets a branded n8n they
own, under their own free licence. Our engine keeps the approval-and-record behaviour for governed work.

## Non-goals

- No multi-tenant or hosted n8n. One instance per client.
- No white-labelling, no embedding n8n behind our UI.
- No gating of n8n access on payment.
- No C7 identity or TLS ingress work; the demo uses the existing tunnel.
- No full template library. Two templates in step 2, more later.

## Architecture

n8n runs as its own service in the client deployment, with its own database on the shared Postgres server,
its own encryption key and its own owner account. It is not exposed publicly in step 2; it sits on loopback
and is reached through the operator tunnel, the same way the product UI is reached today.

Integration points:

1. **Model access through LiteLLM.** n8n gets an OpenAI-compatible credential pointing at
   `http://litellm:4000/v1` with a virtual key minted for the deployment. Model spend and routes stay under
   the gateway. No provider key is pasted into n8n.
2. **Governed jobs through a signed API webhook.** n8n calls `POST /integrations/n8n/jobs` with an
   HMAC-SHA256 signature over the request body. The API authenticates the service principal, creates a job,
   and returns the job id. n8n polls `GET /jobs/{id}` until terminal and consumes the result.
3. **Client-side connector actions stay in n8n.** Those are the client's record, not ours. An optional
   bridge that mirrors execution summaries into our chain is a later add-on, not part of step 2.

## Work packages

### W1. Service, database and secrets (about half a day)

- Add an `n8n` service to the base compose: official `docker.n8n.io/n8nio/n8n` image pinned by digest,
  `restart: unless-stopped`, `127.0.0.1:5678:5678`, `ai-net`, no public bind.
- Its own database `n8n` on the shared Postgres server, created idempotently by the start script, the same
  way the `litellm` database is created today. n8n runs its own migrations on first start.
- Environment: `DB_TYPE=postgresdb`, the shared Postgres host/user/password, `N8N_ENCRYPTION_KEY` generated
  by the prepare script, `N8N_HOST`, `N8N_PORT`, `N8N_PROTOCOL`, `N8N_WEBHOOK_URL`, `N8N_EDITOR_BASE_URL`,
  timezone `America/New_York`, diagnostics and version checks off, execution pruning on, binary data in the
  database so a normal Postgres backup covers it, settings-file permissions enforced.
- A bind mount for `/home/node/.n8n` under the deployment root for the encryption key and any local state.
- Owner account: created on first login, credentials generated by the prepare script and written to a
  mode-600 file, not committed.
- Version selection: pick the current stable at implementation time, record the digest and version in the
  compose comment, and note the upgrade policy (a version bump is tested against both templates).
- Identity detail to verify at implementation: current n8n releases use their own user management. The
  obsolete basic-auth environment variables must not be carried over. The acceptance check includes a real
  login through the tunnel.

### W2. Signed webhook and per-workflow principals (about one day)

- New API route `POST /integrations/n8n/jobs`. Validates the HMAC signature with
  `OI_N8N_WEBHOOK_SECRET`, rejects a missing or wrong signature with 401, and does not create a job on
  failure.
- **Per-workflow integration registry.** The prepare script writes `rendered/n8n_integrations.json` with one
  entry per template: an integration id, a per-integration HMAC secret, the declared task, role and roots, and
  the `owner_subject` who requested the automation. The file is mode 600 because it carries the secrets.
- **Provisioning validation.** For each entry, provisioning checks the owner exists in the rendered access
  registry and that the declared roots are a subset of the owner's roots. A workflow cannot be provisioned
  with more document access than its owner has. This is the per-workflow privilege bound.
- **Webhook shape.** `POST /integrations/n8n/jobs/{integration_id}`. The API loads the integration registry at
  startup, verifies the HMAC over the raw body with that integration's secret, checks the task is declared,
  and creates the job with the integration's role and roots. Missing or wrong signature is refused with 401
  and creates no job.
- **Identity in the record.** Jobs and audit rows carry the automation principal
  (`automation+<integration_id>@<deployment>`) as the actor, and the payload carries `owner_subject` and the
  integration id. The UI shows who requested the automation, not only the machine identity.
- Request body: `{"input": "<text>", "request_id": "<optional>"}`; the task comes from the integration entry.
  Response: the job as JSON, including its id.
- Result retrieval is the existing `GET /jobs/{id}` with a short-lived token issued by the webhook response,
  which is simpler for an n8n HTTP node than a second signed read path.
- Tests: signature valid, missing, wrong; undeclared task; owner with insufficient roots refused at
  provisioning; successful creation and completion; the automation actor, owner and roots visible in the
  audit rows; output access limited to the declared roots.

### W3. Templates and demo flow (about half a day)

- `deploy/n8n/workflows/scheduled-governed-report.json`: a Schedule Trigger calls the signed webhook to start
  a governed `summarise_across_documents` or `draft` job, polls until terminal, then writes the result where
  the client chose (file, email through the connector, or a sheet). For step 2 the last step is a file write
  plus an execution-log assertion, so the acceptance does not depend on a third-party account.
- `deploy/n8n/workflows/invoice-intake-trigger.json` as the second template: a manual trigger calls the
  governed invoice job, which stops at the approval gate; a person approves in our Review screen; n8n shows
  the completed result. This connects the client-owned trigger layer to our approval path.
- A short `deploy/n8n/README.md`: where n8n lives, how to import a template, how credentials are provisioned,
  and the five licensing guardrails from decision 0011.

### W4. Deployment scripts, backup and acceptance (about half a day)

- Prepare: pull the pinned n8n image, generate `N8N_ENCRYPTION_KEY`, owner credentials, webhook secret,
  service principal and the LiteLLM virtual key.
- Start: create the `n8n` database, start the service after Postgres and LiteLLM, wait for its health.
- Backup: include the `n8n` database in the Postgres dump set. The encryption key must be backed up with it,
  or the stored credentials cannot be read after a restore.
- Acceptance record under `docs/reviews/n8n-integration-<date>/` with these checks:
  1. n8n health, login through the tunnel, restart and state persists.
  2. An n8n HTTP node reaches LiteLLM and a spend row appears.
  3. Signed webhook creates a governed job; the chain shows the job, its model call and its tool rows; the
     n8n flow receives the result.
  4. A wrong signature is refused, and no job is created. Provisioning refuses a workflow whose
     declared roots exceed its owner's roots.
  5. A deployment without the `workflow-automation` pack does not start n8n.
  6. The two templates import and run against the pinned version.
- New rows in `docs/requirements.yaml`: `N8N-DEPLOY-001`, `N8N-GATEWAY-001`, `N8N-JOB-001`,
  `N8N-BACKUP-001`, marked verified only when the acceptance record exists.

### Optional later: chain bridge (about one day)

An n8n workflow posts execution summaries to an API endpoint that writes `tool_call` rows with an assigned
data class. This is a mirror, not a transaction guarantee, and it is presented as an add-on.

## Risks and open questions

1. **Licence paperwork.** `BIZ-LICENSE-001` stays open until counsel confirms the contract language. The
   decision and the guardrails are recorded; the grant is not.
2. **Security surface.** n8n can reach many systems and holds client credentials. Loopback plus tunnel until
   C7, then proper ingress, TLS and identity. One instance per client.
3. **Version drift.** n8n releases frequently and sometimes changes environment variables or node behaviour.
   Pin the digest, test both templates on every bump, keep the upgrade cadence explicit.
4. **Backup coupling.** The database dump and the encryption key must travel together.
5. **Per-workflow scope bound to the owner.** If the owner's role changes or they leave, their automation
   keeps the scope it was provisioned with until an operator reviews it. The runbook needs an explicit review
   step on role change and offboarding, and a rotation procedure for the integration secrets.
6. **Webhook secret rotation.** Each integration has its own secret in the rendered file and in an n8n
   credential; rotation has to update both, and the runbook needs the procedure.

## Decisions taken, 2026-11-03

1. **Per-workflow principals, bounded by the requesting person's privileges.** Each template gets its own
   integration identity and declared scope. At provisioning, the scope is validated against the owner's
   current roots: a workflow cannot be given more document access than the person who owns it has. Company
   documents only unless the owner holds the executive root. The job records both the automation identity and
   the owner. Live per-person mapping (a n8n user's current session driving the job) needs C7 identity and is
   deferred.
2. **Exposure: loopback plus the SSH tunnel** for step 2. Public ingress and TLS arrive with C7.
3. **Both templates** are in scope: the scheduled governed report and the invoice-intake trigger.
4. **Chain bridge deferred** and documented as an add-on, revisited when a client needs it.
5. **n8n runs on the product box** for step 2, not a separate host.
